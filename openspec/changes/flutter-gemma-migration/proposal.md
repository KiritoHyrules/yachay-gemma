# Proposal: flutter-gemma-migration

## Intent

Replace the custom `llama.cpp` + JNI + MethodChannel engine (~5000 vendored C++ files, broken streaming, ANR on inference, ~3-4GB RAM) with Google's official `flutter_gemma: ^0.10.0` (MediaPipe/LiteRT native runtime, GPU-accelerated streaming, native tool calling, ~2-3GB RAM). The migration affects only the engine layer; all UI (`yachay-*`) and persistence specs are preserved.

## Scope

### In Scope
- Delete `android/app/src/main/cpp/` (5000+ files), `GemmaEngine.kt`, CMake/GGUF build config
- Add `flutter_gemma: ^0.10.0` to pubspec.yaml
- Rewrite `GemmaService` from 1049-line MethodChannel to ~250-line FlutterGemmaPlugin
- Adapt 13 `ToolRegistry` specs to flutter_gemma `Tool[]` with `supportsFunctionCalls: true`
- HuggingFace OAuth PKCE download pipeline (reuse from reference `gemma-vision`)
- Simplify `FallbackDispatcher` — OOM checkpoint system removed (MediaPipe handles memory)
- Feature-gate `useFlutterGemma` for staged rollout with llama.cpp preservation

### Out of Scope
- `Proyecto referencia/gemma-vision/` (reference only; not vendored)
- Yachay UI layer (`yachay-chat`, `yachay-camino`, `yachay-perfil`, `yachay-dashboard`, `yachay-mastery`, `yachay-curriculum`)
- `fallback_responses.json` (preserved as emergency safety net)
- Database schema changes (SQLite remains unchanged)
- Keystore MethodChannel (preserved in MainActivity.kt)

## Capabilities

### New Capabilities
- `gemma-engine-plugin`: flutter_gemma native engine with streaming `Stream<ModelResponse>`, GPU delegation, and native tool calling
- `model-download-oauth`: HuggingFace OAuth PKCE download for gated `.litertlm` models, with progress tracking and resume

### Modified Capabilities
- `ai-streaming`: MethodChannel EventChannel → native `generateChatResponseAsync()` stream with per-token delivery
- `ai-tool-dispatcher`: XML parsing + GrammarBuilder → flutter_gemma `Tool[]` with `FunctionCallResponse`
- `ai-fallback`: OOM checkpoint system removed; FallbackDispatcher simplified to emergency-only

### Unchanged
- `ai-sampling`, `yachay-chat`, `yachay-camino`, `yachay-curriculum`, `yachay-dashboard`, `yachay-mastery`, `yachay-perfil`

## Approach

**Strategy**: Incremental with feature flag — `useFlutterGemma` gate allows A/B testing against legacy llama.cpp path. Migration is additive until verified, then llama.cpp path is deleted.

1. **Build cleanup**: Remove CMake/GGUF from build.gradle, delete `cpp/` directory, remove GemmaEngine.kt MethodChannel (keep Keystore channel).
2. **Plugin integration**: Add `flutter_gemma: ^0.10.0`, implement `FlutterGemmaPlugin.instance` singleton pattern (reference: `gemma-vision/lib/chat_page/services/gemma_service.dart`).
3. **Model download**: Reuse HuggingFace OAuth PKCE flow from reference project (`huggingface_oauth.dart` → token exchange → `FlutterGemma.installModel().fromNetwork()`).
4. **Streaming rewrite**: Replace MethodChannel `generateStream` with native `InferenceChat.generateChatResponseAsync()` returning `Stream<ModelResponse>`.
5. **Tool adaptation**: Map 13 `ToolSpec` entries to `Tool(functionName, description, parameters)` with `supportsFunctionCalls: true`.
6. **Fallback simplification**: Remove `_recoverFromOom()`, `_purgeOldCheckpoints()`, `oom_checkpoints.db` — MediaPipe handles memory. Keep 4-layer `FallbackDispatcher` for emergency.

**Model strategy**: Primary target is Gemma 3n E2B IT (.task) — proven in reference app. Gemma 4 E2B (.litertlm) is stretch goal via `litert-community/gemma-4-E2B-it-litert-lm` (gated).

## Risks

| Risk | L/M/H | Mitigation |
|------|-------|------------|
| Gemma 4 .litertlm gated on HuggingFace | H | Use Gemma 3n .task (proven). Implement OAuth. Gemma 4 is stretch. |
| flutter_gemma API break between versions | M | Pin to ^0.10.0. Reference app already uses this version. |
| Tool calling behavior differs from XML dispatch | L | Native tool calling is more robust. Port 13 specs with same semantics. |
| APK size increase from MediaPipe runtime | L | Still under 50MB target. Model is external. |
| Stream response format differs (ModelResponse vs raw tokens) | L | flutter_gemma emits per-token TextResponse — matches current token callback contract. |

## Rollback Plan

**Feature flag**: `static bool useFlutterGemma = true;` in `GemmaService`. When `false`, routes to preserved legacy `_legacyLoadModel()` using MethodChannel. The llama.cpp code is kept on a `legacy-llamacpp` branch (`git branch legacy-llamacpp HEAD~0`). Rollback is a one-flag change: `useFlutterGemma = false` → app falls back to existing flow. No data migration needed.

After hackathon verification, the llama.cpp path and `legacy-llamacpp` branch are deleted as cleanup.

## Dependencies

- `flutter_gemma: ^0.10.0` (pub.dev)
- `flutter_web_auth_2: ^4.1.0` (OAuth browser redirect — from reference)
- `http: ^1.4.0` (token exchange — already in project)
- Gemma 3n E2B IT `.task` model (primary) or Gemma 4 E2B `.litertlm` (stretch)

## Success Criteria

- [ ] `flutter build apk --debug` succeeds with zero CMake/JNI references
- [ ] Streaming tokens arrive via `generateChatResponseAsync()` with <3s TTFT on 2GB device
- [ ] All 13 tools execute via native `FunctionCallResponse` with correct semantics
- [ ] HuggingFace OAuth downloads model to MediaPipe cache directory
- [ ] Feature gate `useFlutterGemma=false` falls back to llama.cpp with zero code changes
- [ ] Fallback system still routes all 4 layers when model unavailable
