# Exploration: flutter-gemma-migration

## Executive Summary

**Verdict: RECOMMENDED with HIGH confidence.** Migrating to `flutter_gemma` (^0.10.0) eliminates ~5,000+ lines of vendored C++ code, replaces a fragile custom JNI bridge with Google's official MediaPipe/LiteRT runtime, enables real streaming, solves the ANR problem, and provides native tool calling. The main tradeoff is that we lose the GGUF model ecosystem — we must use `.litertlm` format models for Gemma 4, which are gated on HuggingFace and require OAuth for download.

**Model format gap**: The `google/gemma-4-E2B-it-qat-mobile-transformers` repo contains Safetensors/PyTorch weights and GGUF Q4_0 — NOT the `.litertlm` format flutter_gemma needs. The correct model is at the gated `litert-community/gemma-4-E2B-it-litert-lm` repo. For Gemma 3, `.task` files work (as the reference gemma-vision uses).

## Gap Analysis

### What flutter_gemma provides vs what we need

| Feature | Current (llama.cpp) | flutter_gemma | Gap |
|---------|-------------------|---------------|-----|
| **Model loading** | MethodChannel → JNI → llama.cpp | `FlutterGemma.getActiveModel()` | ✅ Solved — no JNI, no CMake |
| **Streaming** | Broken — blocking inference on main thread via MethodChannel | Native `Stream<ModelResponse>` via `generateChatResponseAsync()` | ✅ Solved — true async stream |
| **ANR risk** | High — 30s blocking calls | Low — native background threads via MediaPipe | ✅ Solved |
| **Tool calling** | Custom XML parsing + dispatch loop (13 tools) | Native `Tool` class + `FunctionCallResponse` | ✅ Easier — adapt 13 tools to `Tool[]` format |
| **GPU support** | No (CPU-only llama.cpp on Android) | Yes — MediaPipe delegates to GPU/NPU | ✅ Better inference speed |
| **Model download** | Manual GGUF via scripts/download_model.py | Built-in `FlutterGemma.installModel().fromNetwork()` with OAuth | ✅ Simpler pipeline |
| **Gemma 4 support** | GGUF quantized variants (IQ1_S, IQ2_XXS, IQ2_M) | `.litertlm` format (newer, optimized for LiteRT) | ⚠️ Model format change required |
| **Gemma 3 support** | GGUF | `.task` format (MediaPipe) | ⚠️ Different model file needed |
| **Fallback system** | Custom `FallbackDispatcher` (4 layers) | Not applicable — model always available if installed | 🔄 Adapt — keep as safety net |
| **13-tool registry** | XML parsing via `ActionParser` + `GrammarBuilder` | `Tool[]` class + `supportsFunctionCalls: true` | 🔄 Rewrite — simpler, native support |
| **OOM recovery** | Custom SQLite checkpoint DB | Not needed — MediaPipe manages memory | ✅ Remove checkpoint code |
| **Peruvian Spanish prompts** | Hardcoded system prompts | `systemInstruction` parameter | 🔄 Transfer prompt strings |

### Memory Comparison

| Aspect | llama.cpp GGUF | MediaPipe .litertlm |
|--------|---------------|---------------------|
| **Model size (Gemma 4 E2B)** | IQ2_M: ~2.6GB, IQ2_XXS: ~2.0GB, IQ1_S: ~1.7GB | ~1.5-2GB (estimated, wNa8o8 optimizations) |
| **Runtime RAM** | Full model + KV cache + llama runtime (~3-4GB) | Model delegates to GPU, MediaPipe shares memory (~2-3GB) |
| **GPU offloading** | Not on Android ARM | Yes — NNAPI, GPU delegate |
| **KV cache** | Manual via `ramTier` (F16/Q8_0/Q4_0) | Managed by MediaPipe runtime |
| **OOM risk** | High — custom checkpoint system | Low — MediaPipe handles gracefully |

**Conclusion**: MediaPipe generally uses LESS RAM because it can delegate compute to the GPU and uses channel-wise quantization (the wNa8o8 schema uses 2-bit decoding layers specifically for mobile efficiency). On a 2GB device, this is the difference between "barely works" and "works comfortably."

## Migration Scope

### Files to DELETE

**Android native layer (entire directory):**
- `android/app/src/main/cpp/` — CMakeLists.txt, gemma_engine.cpp, gemma_engine_stub.cpp, llama.cpp/ (~5000+ files)

**Kotlin bridge (entire file):**
- `android/app/src/main/kotlin/.../GemmaEngine.kt` (576 lines) — MethodChannel handler, JNI declarations, OOM checkpoint, RAM tier detection, TokenCallback

**Build configuration (modifications):**
- `android/app/build.gradle` — Remove `externalNativeBuild` block (lines 56-61), remove `aaptOptions.noCompress 'gguf'` (lines 52-54), optionally remove `ndk.abiFilters 'arm64-v8a'`

**Dart service (full rewrite):**
- `lib/modules/gemma/gemma_service.dart` (1049 lines) — Replace MethodChannel with FlutterGemmaPlugin

**Dart files that become simpler:**
- `lib/modules/gemma/grammar_builder.dart` — Remove (grammar is auto-generated by flutter_gemma from Tool schemas)
- `lib/modules/gemma/action_parser.dart` — Remove (flutter_gemma natively parses function call responses)

**No longer needed:**
- `scripts/download_model.py` — Replaced by flutter_gemma's built-in download
- `assets/data/fallback_responses.json` — Can keep but role changes (model should always work)

### Files to MODIFY

**pubspec.yaml:**
- Add: `flutter_gemma: ^0.10.0`
- Remove (optional): `path_provider` if no longer needed for model path detection
- Keep: all existing dependencies (provider, sqflite_sqlcipher, etc.)

**MainActivity.kt:**
- Remove: GemmaEngine instantiation and registration (lines 14, 39-45)
- Keep: Keystore MethodChannel (lines 20-36)
- flutter_gemma handles its own engine registration automatically

**lib/modules/gemma/gemma_service.dart:**
- **FULL REWRITE** — Replace 1049 lines with ~200-300 lines using flutter_gemma API
- New API surface:
  ```dart
  class GemmaService {
    final _gemma = FlutterGemmaPlugin.instance;
    InferenceModel? _model;
    InferenceChat? _chat;
    
    Future<bool> cargarModelo() async { ... }
    Future<String> procesarMensaje(String message) async { ... }
    Future<void> sendWithStreaming(...) async { ... }
    Future<void> dispose() async { ... }
  }
  ```

**lib/modules/gemma/tool_registry.dart:**
- Adapt 13 tool specs from custom format to flutter_gemma `Tool` objects

### Files to ADD

- `lib/modules/gemma/model_download_service.dart` — Model download wrapper using `FlutterGemma.installModel()`
- `lib/modules/gemma/tool_registry.dart` — Refactored ToolRegistry using flutter_gemma Tool class

## API Mapping

| Current API | flutter_gemma API | Notes |
|------------|-------------------|-------|
| `cargarModelo(path?)` | `FlutterGemma.installModel().install()` + `FlutterGemma.getActiveModel()` | No manual path needed — plugin manages cache |
| `procesarMensaje(msg)` | `chat.addQueryChunk()` + `chat.generateChatResponseAsync()` | Stream-based, returns tokens progressively |
| `sendWithStreaming(prompt, ...)` | `chat.generateChatResponseAsync().listen()` | Native stream — no separate stream channel needed |
| `generarExplicacion(tema)` | Same as procesarMensaje with formatted prompt | Can be consolidated |
| `generarEjerciciosRefuerzo(tema)` | Same as procesarMensaje with formatted prompt | Can be consolidated |
| `dispose()` | `model.close()` + `modelManager.deleteModel()` | Cleaner, no channel cleanup needed |
| `_getRamTier()` | Not needed — MediaPipe auto-detects hardware | Remove entire RAM tier logic |
| `_recoverFromOom()` | Not needed — MediaPipe handles memory | Remove entire OOM checkpoint system |
| `ToolRegistry` | `List<Tool>` + `supportsFunctionCalls: true` | Simpler, type-safe |
| `FallbackDispatcher` | Keep but adapt — model should always load | Reduce to emergency-only |

## Model Availability

### Gemma 4 (.litertlm format)

| Model | Repo | Status |
|-------|------|--------|
| Gemma 4 E2B IT | `litert-community/gemma-4-E2B-it-litert-lm` | 🔒 Gated (requires HF login + license) |
| Gemma 4 E4B IT | `litert-community/gemma-4-E4B-it-litert-lm` | 🔒 Gated |

The `google/gemma-4-E2B-it-qat-mobile-transformers` repo (Apache 2.0, ungated) provides Safetensors/PyTorch weights and GGUF Q4_0 — these are NOT compatible with flutter_gemma directly. The mobile-optimized wNa8o8 format IS designed for MediaPipe but is not yet distributed as `.litertlm`. This is the main **risk**.

### Gemma 3 (.task format)

| Model | Repo | Status |
|-------|------|--------|
| Gemma 3n E2B IT Int4 | `google/gemma-3n-E2B-it-litert-preview` | ✅ The reference app uses this |

### Fallback plan

If Gemma 4 .litertlm is not available in time for hackathon:
1. **Use Gemma 3n E2B IT (.task format)** — proven working in reference app
2. **Keep Gemma 4 as stretch goal** — once Google releases official .litertlm, swap models
3. **Keep fallback_responses.json** — still works as emergency safety net

## Risk Assessment

| Risk | Severity | Likelihood | Mitigation |
|------|----------|------------|------------|
| **Gemma 4 .litertlm model gated** — requires HuggingFace OAuth | Medium | High | Implement OAuth (reference app already has full OAuth flow). Fallback: use Gemma 3n .task. |
| **Inference performance regression** — MediaPipe may be slower than llama.cpp in some scenarios | Low | Low | flutter_gemma uses MediaPipe GPU delegate — should be faster. Profile first. |
| **Plugin API changes** — flutter_gemma is actively developed | Medium | Medium | Pin to ^0.10.0. Test before upgrading. |
| **Loss of 13-tool dispatch loop flexibility** — XML parsing gave us full control | Low | Low | Native tool calling is more robust and LLM-agnostic. |
| **App size increase** — flutter_gemma adds ~15-30MB to APK | Low | Medium | Still well under 50MB target. Model is external. |
| **Model format confusion** — wNa8o8 ≠ .litertlm ≠ .gguf | Medium | Medium | This exploration doc serves as reference. Only use .litertlm for Gemma 4. |

## Recommendation

**PROCEED with migration.** The benefits are overwhelming:
1. Eliminates 5000+ vendored C++ files — maintenance burden gone
2. Real streaming — no more token batching workarounds
3. No ANR risk — proper async threading
4. Native tool calling — simpler than XML dispatch
5. GPU acceleration — better performance on mobile

**Strategy for Gemma 4**: Use Gemma 3n E2B IT (.task) as the primary model for the hackathon (proven working in reference app). Add Gemma 4 E2B (.litertlm) as stretch goal once we implement the HuggingFace OAuth download flow.

**Immediate prerequisite**: Verify `flutter_gemma: ^0.10.0` compiles with our Flutter SDK version. Run `flutter pub add flutter_gemma` in a test branch first.
